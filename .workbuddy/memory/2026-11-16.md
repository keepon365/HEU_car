## 14:05 v2.3：转向改用原地旋转，方向反相，修掉死掉的 DUTY_TURN

### 用户反馈（实测）
1. 圆盘左右（单边转弯）→ 车**完全没反应**
2. 底部「原地左旋/右旋」→ 工作正常、效果很好（近似原地转向）
3. 但按"左旋"实际往右转 —— 方向反了
4. 结论：干脆用旋转代替转弯，删掉多余的按钮

### 根因 1：转弯为什么没反应（不是 App 的错）
`DUTY_TURN = 65`，乘 SPEED 后 `TURN = 72`。
而源码注释自己写着「下限约 80：再低要克服内侧轮拖滑阻力 + 左轮起转门槛 73」。
72 < 73 → 单边轮推不动 → 按键发码正常但车纹丝不动。
这个值从 SPEED=1000 时代就低于门槛，所以转弯功能**从来没生效过**，
用户自然也从没测出过转弯方向。
→ 改为 `DUTY_TURN = 85`（×1.2 = 102）。作用只剩兼容旧版 App。

### 根因 2：旋转方向
KEY_TABLE 原本：左旋 = 左轮后退 + 右轮前进（俯视逆时针 = 车头左偏）
用户实测看到的是右转 → 按要求把两行方向互换。
现在：左转 = 左轮前进 + 右轮后退（俯视顺时针）
⚠️ 若用户再反馈"又反了"，说明他与几何定义差一个镜像，把那两行再翻一次即可。

## 超声波无回波定位（20:10）

  正常现象，不能据此判短路。必须用模拟量看中间值才能分开"短地"和"无供电"。

## 看距离.bat 断线的处理（20:37）

现象：用户窗口跑约 5 秒后自己退出，退出前打 `[port released]`，开头还有一串乱码。
乱码 = DTR 复位进 bootloader，以错误波特率输出。

两处修改（bat 内）：
1. `-c dtr=off -c rts=off` → 开串口不再复位板子，乱码消失（实测有效）
2. `:loop` 自动重连 + `ping -n 2 127.0.0.1 >nul` 延时（**不能用 `timeout /t`**：
   非交互 stdin 下会报 Input redirection is not supported）
   `mode con:` 非真实控制台会报错，须加 `>nul 2>&1`

疑似根因：**小车电池的 5V 往 USB 供电倒灌**（VCC 实测 5308mV，比 USB 5.0V 高）。
USB 串口芯片被顶掉 → COM9 消失 → monitor 退出。待用户拔电池验证。
本机自己跑 45s 不断，说明固件没问题。

## 360 舵机极性 + 脚位定案（2026-11-17）

## 比赛模式 + 修复遛狗结束无效（2026-11-17 14:20）v2.6 / versionCode 8

### ★ 比赛模式换向死循环（实测踩到，务必记住）

## 更新下载到旧包 → "已安装更高版本"（2026-11-17 14:30）v2.7 / versionCode 9

现象：手机装 2.5(7)，App 提示有新版 2.6(8)，点更新后系统报"已安装更高版本"。

根因链（三个都成立才会这样）：
1. `Updater.download()` 只校验「文件大小 ≥8KB」+「PK 头」，**不校验 versionCode**
   → 镜像/Release 返回 v2.4 那批旧包（≤6）时，被当成"下载成功"
2. 旧包交给安装器：包里 6 < 已装 7 → 系统拒绝，用户看到"已安装更高版本"
3. `onBannerTap` 里 `Updater.apkReady()` 无条件复用本地包
   → 旧包永远躺在那儿，点多少次都是同一个，**再也下不到新版**

修复（v2.7）：
- 新增 `apkVersionCode(ctx, file)`：用 `PackageManager.getPackageArchiveInfo` 读**APK 文件**自带
  的 versionCode（不是已安装的）
- download 增加 expectCode 参数，下完必须相等，否则删除文件并报
  "下载到的是 vX，不是 vY（镜像缓存还没刷新）"
- URL 加 `?v=<目标版本>` 换缓存键，绕开 CDN 旧缓存
- install() 前再校一遍：inApk 必须 > 已装，否则删文件返回 false
- 点横幅时若 `cachedApkCode != upCode` → 丢弃重下，不再盲目复用

★ 教训：**只校验"像不像 APK"是不够的，必须校验"是不是我要的那个版本"。**
  文件大小和 PK 头在旧包上全都正常。

★ 鸡生蛋：修复在 2.7 里，但 2.5 的更新逻辑自己是坏的，下不到 2.7。
  必须让用户**手动装一次**（浏览器直链 / 微信传文件 / adb），之后链路才正常。

推送：fc9866b（这次直连被 reset，走 127.0.0.1:7890 代理成功）。

## v2.7 装上闪退 → 根因是构建脚本吞掉 javac 错误（2026-11-17 14:38）v2.8 / vc 10

现象：用户装 v2.7 后「完全打不开」。

★ 根因（值得永久记住）：
  `Updater.java` 里新加的版本校验写成 `final int apkCode`… 不，是 `final int got`，
  而同一个 run() 里第 155 行已有 `long got = 0`（统计已下载字节），
  javac 报 `variable got is already defined` → **编译失败**。
  但 `build_apk.sh` 用 `set +e` 包住 javac，且只做
  `test -f MainActivity.class || exit 1`：
  javac 失败时会**部分产出**，MainActivity.class 照样存在 → 检查通过 → 构建走完。
  结果：dex 只有 30128B，**缺 Updater.class / UpdateConfig.class**，
  MainActivity 引用不到的类 → 启动即崩（NoClassDefFoundError），
  而 version.json 还报了新版本号，看着像"发布成功"。

修复：
1. Updater.java 变量改名 `apkCode`
2. build_apk.sh javac 后取 `${PIPESTATUS[0]}`，非 0 **立即 exit 1**，
   不生成 APK / version.json
3. 再加一道：遍历 sources.txt，每个 .java 必须有同名 .class，缺一个就中止
4. sources.txt 是 cygpath -w 的**反斜杠**路径，sed 前要 `s|\\|/|g`

验证：
- build/classes 共 24 个 class，Updater.class / Updater$Cb.class 都在
- dex 38084B，含 Updater / UpdateConfig / MainActivity / ApkProvider 四个主类
- APK 45857B（与完整版 v2.5 一致；损坏的 v2.7 只有 41761B）
- aapt2: versionCode=10 versionName=2.8，清单校验一致
- 镜像 ghfast.top / gh-proxy.com 均 200，md5 均为 4e69e03cb690

推送：fc9866b..8657dab（经 127.0.0.1:7890 代理）。
桌面已放 ZYAR20A_v2.8.apk 供手动安装（手机上现在是打不开的 2.7/vc9，10>9 可覆盖）。

★ 教训两条：
  1. **构建脚本对"编译失败"必须硬失败**。只检查某个产物存在是不够的，
     javac/d8 都可能部分成功。
  2. APK 变小的方向很可疑：新增功能却比上一版小 → 十有八九是类没打进去。

## 自动模式改版：蜂鸣 + 15 度细扫 + 修"几乎不左转"（2026-11-17 15:00）

### ★ 蜂鸣器绝对不能用 tone()
AVR 上 IRremote 用 **Timer2**（IRremoteInt.h 里 `IR_USE_TIMER2` → `TIMER2_COMPA_vect`），
而 Arduino 的 tone() 同样占 Timer2 —— 一响，红外接收立刻失效，车就不听遥控。
所以蜂鸣器用 **micros() 软件方波**（A3），非阻塞音序，不碰任何定时器。
结构：BuzzStep{freq,ms} 数组 + buzzPlay()/serviceBuzzer()，freq=0 表示静音段。
三种音：SEQ_START（1000→1500 两声）、SEQ_STOP（520 一声）、SEQ_PICK（三声急促）。
串口 B / B1 / B2 自检。DOG_BEACON 阶段语义改为"等启动音播完再扫描"。

### 扫描按模式分表
- 遛狗 `DOG_ANGLES` 5 档 30°：settle 150ms、采样 5×40ms
- 比赛 `RACE_ANGLES` 9 档 15°：settle 90ms、采样 3×35ms
运行时用 `scanAngles/scanN/scanSettleMs/scanSamples/scanGapMs`，
数组按 `SCAN_MAX_N(9)` 分配。比赛一轮扫描 3.1s → 1.4s。

### ★★ "几乎没有左转"是三个原因叠加，逐个拆开
a) **固定右转**：比赛走完一段就 `dogTurn(..., +1, ...)` 转 120°，三次=360°，
   车一直顺时针扫场 → 目标几乎总在右侧。改成：推过东西→蜂鸣+180°，
   没推过→直接回扫描不转向，左右完全由目标位置决定。
b) **空场也右转**：`dogTargetIdx<0` 时固定 `dogTurn(420ms,+1,SCAN)`。
   比赛改为直走一段（空场就该往前开）。
c) **侧边车体假回波**：`DOG_MIN_CM` 降到 5cm 后，舵机打到 150/30 时
   车头零件/线束的 12~16cm 读数成了"最近目标"，车一路朝它转。
   新增 `DOG_EDGE_DEG 45` / `DOG_EDGE_CM 18`：侧边档位用更高门槛。
   `dogMinCmFor(i)` 统一算门槛，dogPick 和地图打印共用。
   **地图里用 `!` 标出被挡掉的档**，一眼能看出哪些是假目标。

DOG_DEAD_DEG 18→20（让 15° 档直接走：52ms 脉冲电机来不及起转，超声锥角本来就 15°）

## 微调精度 + 正前方确认 + 走歪误判 + 短步（2026-11-17 15:55）commit e7c24ad

### 1. 微调精度：三段叠加失败
- **降速**：微调专用 `DUTY_AIM=78`（大角度仍 DUTY_SPIN=119）。
  290°/s 是 2800ms 转 2.2 圈标出的**稳态**速度；103ms 的脉冲里前 60ms
  都在克服静摩擦，实际只转 12°。降速后 30° 要 200ms，线性度好得多。
- **补偿**：`TURN_COMP_MS=50`，只对 ≤45° 生效（大角度会过转）。
- **增量逼近**：上次微调后目标还在同一档、距离没近 → 脉冲 ×1.8。
  这是关键：不依赖标定，电池/地面变化都能收敛。
- 串口 `Q`（转 3 秒数圈）/ `Q<dps>` 标定微调角速度 `aimDps`（默认 150）。

### 2. 正前方确认（用户要求"最近必须被正前方扫到"）
对准到 ±15° 后不直接走：回中 → 120ms → 实测一发 → 通过才前进。
阈值 `RACE_CONFIRM_SLACK=20`。原因：105° 档偏 15° 正在锥角边缘，
斜着看得到不代表正前方有它，直走会从旁边擦过。

### 3. ★ 走歪导致距离变长的精确解法（几何）
目标偏 θ 角时读数是**斜距 d/cosθ**：20cm 偏到 45° 读成 28.3cm（+8.3cm），
刚好越过"回升 8cm = 收到"的阈值 → 走歪被误判成收到。
解法：`eff = d × cos(θ)`，两边都折算回正前方再比（查表 COS1000）。
不用加扫描轮次，也不用把阈值调大（那会漏判真收集）。

### 4. 短步推进
- `RACE_GO_MS` 1000 → **400**（约 20cm）
- 途中连续 3 次距离不变近（且 <45cm）→ 提前刹车（RACE_STALL_N=3）
- 走完先 60ms 快测一发（`DOG_QUICK`），还在接近就直接再走一段，
  只有出问题才全扫 → 正常前进是"走 400ms + 测 60ms"循环

### ★ 自己引入又修掉的 bug
overrun 的 1200ms 被"距离不再变小"腰斩：推物块时距离本来就不变，
150ms 就被判停，物块推不进去。修法：条件加 `!dogPushDone`。

```
                → 上一轮没转够 → 转向 右 R 450ms 微调低速
                → 正前方确认 OK 7cm → 贴到 7cm 推 1200ms → 推满 → 转 620ms
```
