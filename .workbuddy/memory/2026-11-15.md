## 23:05 更正：上面「LSB 先发」的结论是错的（这是"按了没反应"的真正根因）

- 重新完整反汇编旧版 classes3.dex 的 NecSender$Companion.encode(long)：
  循环 `for (bit = 31; bit >= 0; bit--)`，`ushr-long v5, code, v2` —— **高位先发（MSB first）**
- 为什么必须高位先发：车端 IRremote 的 decodeNEC 是
  `data = (data << 1) | bit`，最先收到的位进最高位。
  所以要让车端解出 0x00FF629D，发送端就必须先发 bit31。
- 旧版（能用的那版）发 LSB 的话车端会解成 0xB946FF00，KEY_TABLE 一条都不命中
  → App 日志显示发送成功、车一动不动 —— 完全吻合本轮的故障现象
- 修复 v2.1：necFrame() 改为 bit31→bit0、数组 67 个（末位补 space），
  发射改成旧版同款：单帧一次 transmit + sleep 45ms 帧间隔 + 单条 HandlerThread
  （删掉 stopQueue，避免两条线程同时调 transmit 打断波形）
- 校验：app/verify_waveform.py 证明新编码器与旧版逐元素相同，且都能解回正确键码
- 教训：compare 波形不能只比 9000/4500/560/1690 这些常量，位序同样致命

## 23:35 ★ 严重 bug：SPEED≠1000 时车完全不动（AVR 16 位整数溢出）

- 现象：用户反馈「车不动了，SPEED=1000 才动」
- 串口读回 `[CAL] L=256 R=225 S=1100 FWD=1 TURN=6` —— 前进占空比算出 **1**
- 根因：scaleSpeed() 用 `(uint16_t)duty * speedPermille`。
  AVR 的 int 只有 16 位，120×1100=132000 → 回绕成 928 → /1000 = **1**
- 为什么只有 1000 能跑：函数开头 `if (speedPermille == 1000) return duty;`
  短路分支不做乘法，所以 bug 只在改过速度后暴露。
  这也解释了之前「调 SPEED 没感觉」——所有档位都被压成 1~53
- 反算验证（修复前实读全部吻合溢出值）：
  前进 120×1100→928→1 ｜ 后退 96×1100→40064→40 ｜
  转弯 65×1100→5964→6   ｜ 旋转 108×1100→53264→53
- 修复：`const uint32_t d = ((uint32_t)duty * speedPermille + 500)/1000;`
- 全文件排查其余乘法：buildDuty(duty 已是 uint32_t)、rampedDuty((uint32_t)span*held)、
  deadman((uint32_t)frameGapAvg*DEADMAN_PCT)、trim*fadeEnd(≤65025) 均安全
- 修复后逐档实测：900→108 ｜ 1000→120 ｜ 1100→132 ｜ 1200→144 ｜ 1300→156 ｜ 1400→168（线性）
- 已烧录 COM9，横幅确认 前进 duty=132
- 教训：AVR 上 duty(≤255) × 三位数 必须显式 uint32_t 提升；16 位回绕不会报错，只会静默算出垃圾值
